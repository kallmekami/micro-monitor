# Micro Monitor

یه پروژه کوچیک سیستم‌های توزیع‌شده که مصرف CPU و RAM یه سرور رو به صورت
real-time مانیتور میکنه، با معماری میکروسرویس و Docker، و Redis به عنوان
لایه ارتباطی بین سرویس‌ها.

این پروژه به عنوان یه تمرین عملی برای یادگیری طراحی میکروسرویس ساخته شده،
مشخصاً برای بررسی این موضوع که چطور سرویس‌های مستقل میتونن بدون اینکه
مستقیماً به هم وابسته باشن با هم ارتباط برقرار کنن — با استفاده از الگوی
publish/subscribe به‌جای فراخوانی مستقیم سرویس به سرویس.

---

## ۱. انگیزه پروژه

اکثر مثال‌های ابتدایی میکروسرویس از HTTP request بین سرویس‌ها استفاده
میکنن (سرویس A مستقیم endpoint سرویس B رو صدا میزنه). این روش کار میکنه،
ولی باعث coupling بالا میشه: سرویس A باید آدرس سرویس B رو بدونه، باید
retry رو خودش مدیریت کنه اگه B در دسترس نبود، و اساساً این دو تا به هم
چسبیدن.

هدف این پروژه استفاده از یه رویکرد **event-driven** بود. سرویس‌ها به‌جای
صدا زدن مستقیم همدیگه، رویداد رو روی یه پیام‌رسان (در اینجا Redis)
پابلیش میکنن و بقیه سرویس‌ها به چیزی که براشون مهمه ساب‌اسکرایب میکنن.
هیچ سرویسی از وجود سرویس دیگه خبر نداره، فقط Redis رو میشناسه.

---

## ۲. دید کلی سیستم

سیستم از ۴ تا کانتینر تشکیل شده:

```
                    +--------------+
                    |    Redis     |
                    |  (pub/sub)   |
                    +------+-------+
            publish        |        subscribe
        +-------------------+-------------------+
        |                   |                   |
+---------------+   +---------------+   +---------------+
|  collector    |   | alert         |   |  dashboard    |
|  میخونه CPU/  |   | چک میکنه      |   |  نمایش CLI    |
|  RAM رو       |   | threshold ها  |   |  (rich/TUI)   |
+---------------+   +-------+-------+   +-------^-------+
                            |  publish           |
                            +-- channel "alerts"-+
```

| سرویس | نقش |
|---|---|
| collector | مصرف CPU/RAM سیستم رو میخونه و پابلیش میکنه |
| alert | متریک‌ها رو چک میکنه، اگه از threshold رد شد alert میزنه |
| dashboard | رابط ترمینالی که متریک‌ها و alert ها رو زنده نشون میده |
| redis | پیام‌رسان، یه سرویس آماده‌ست نه چیزی که خودمون نوشتیم |

دو تا channel استفاده شده:

| Channel | Publisher | Subscriber(s) | محتوا |
|---|---|---|---|
| `metrics` | collector | dashboard, alert | `{cpu, ram, timestamp}` |
| `alerts` | alert | dashboard | `{type, value, threshold, message, timestamp}` |

## ۳. چرا Redis Pub/Sub به‌جای HTTP؟

این تصمیم اصلی طراحی پروژه بود، پس ارزش داره بیشتر توضیحش بدم.

با روش معمول REST، اگه `collector` میخواست هم به `dashboard` و هم به
`alert` خبر بده، باید دو تا HTTP request جدا میزد، آدرس هر دو رو
میدونست، و حالتی که یکیشون در دسترس نیست رو هم مدیریت میکرد. اضافه
کردن یه consumer جدید بعداً یعنی باید کد `collector` رو مستقیم تغییر
میدادی.

با pub/sub، `collector` فقط یه پیام روی یه channel پابلیش میکنه و
نیازی نیست بدونه کی، یا چندتا سرویس، دارن گوش میدن. اضافه کردن یه
consumer جدید بعداً (مثلاً یه سرویس logging که متریک‌ها رو توی فایل
ذخیره کنه) هیچ تغییری توی کد `collector` نیاز نداره. فقط کافیه به همون
channel ساب‌اسکرایب کنه.

نکته منفی‌اش اینه که pub/sub توی Redis **fire-and-forget** هست: اگه
یه subscriber دقیقاً همون لحظه‌ای که پیام پابلیش میشه وصل نباشه، اون
پیام رو از دست میده. هیچ صف پیامی یا persistence وجود نداره (این با
چیزی مثل RabbitMQ یا Kafka فرق داره). برای یه use case مانیتورینگ که
هر ۲ ثانیه یه reading جدید میاد، این موضوع قابل قبوله، چون از دست دادن
یه reading اتفاق مهمی نیست.

## ۴. جزئیات سرویس‌ها

### ۴.۱ collector

با کتابخونه `psutil` مصرف CPU و RAM رو میخونه و یه payload به فرمت
JSON روی channel `metrics` با فاصله زمانی مشخص (پیش‌فرض هر ۲ ثانیه،
قابل تنظیم) پابلیش میکنه.

اولین فراخوانی `psutil.cpu_percent()` همیشه `0.0` برمیگردونه چون به
یه نمونه قبلی برای مقایسه نیاز داره — کد این رو در نظر گرفته و اولین
reading رو نادیده میگیره.

### ۴.۲ alert

روی `metrics` ساب‌اسکرایب میشه. توی هر reading که میاد، مقدار CPU و
RAM رو با threshold های قابل‌تنظیم (پیش‌فرض ۸۰٪ CPU، ۸۵٪ RAM) مقایسه
میکنه. اگه از threshold رد شد، یه پیام روی channel `alerts` پابلیش
میکنه.

یه cooldown ده ثانیه‌ای برای هر نوع متریک پیاده‌سازی شده، تا اگه CPU
برای مدت طولانی بالای threshold بمونه، سیستم برای هر reading یه alert
جدید نزنه — فقط یه بار alert میزنه، بعد اگه هنوز بالا بود و cooldown
تموم شد، دوباره.

### ۴.۳ dashboard

به هر دو channel (`metrics` و `alerts`) توی دو thread جدا ساب‌اسکرایب
میشه، و یه رابط ترمینالی زنده با کتابخونه `rich` رندر میکنه. این یه
رابط کاملاً command-line هست؛ هیچ web server یا بخش browser‌محور توی
کل پروژه وجود نداره.

dashboard این موارد رو نشون میده:
- یه نمایش به سبک progress-bar برای مصرف فعلی CPU و RAM، با رنگ‌بندی
  بر اساس شدت (سبز / زرد / قرمز)
- یه لیست اسکرول‌شونده از آخرین alert هایی که دریافت شده

## ۵. اجرای پروژه

### پیش‌نیازها
- Docker
- Docker Compose (نسخه ۲، دستور `docker compose`، نه نسخه قدیمی
  standalone `docker-compose`)

### مراحل اجرا

پروژه رو clone یا unzip کن، بعد از پوشه اصلی:

```bash
docker compose up --build
```

این دستور ۴ تا کانتینر بالا میاره: `mm-redis`, `mm-collector`,
`mm-alert`, و `mm-dashboard`.

dashboard به عنوان یه برنامه تعاملی توی ترمینال اجرا میشه، پس بهترین
راه برای دیدنش اینه که مستقیم بهش attach بشی:

```bash
docker attach mm-dashboard
```

برای detach شدن بدون متوقف کردن کانتینر، از `Ctrl+P` و بعدش `Ctrl+Q`
استفاده کن.

برای دیدن لاگ سرویس‌های collector یا alert:

```bash
docker compose logs -f collector
docker compose logs -f alert
```

برای متوقف کردن همه چیز:

```bash
docker compose down
```

### بررسی دستی Redis

میشه channel های pub/sub رو با `redis-cli` به‌صورت دستی بررسی کرد، که
برای دیباگ یا نشون دادن اینکه پیام‌ها واقعاً از طریق Redis رد و بدل
میشن (نه یه مکانیزم دیگه) مفیده:

```bash
docker exec -it mm-redis redis-cli
> SUBSCRIBE metrics
```

## ۶. تنظیمات

تمام تنظیمات از طریق environment variable هایی که توی
`docker-compose.yml` تعریف شدن انجام میشه، و نیازی به rebuild کردن
image ها برای تغییرشون نیست.

| متغیر | استفاده در | پیش‌فرض | توضیح |
|---|---|---|---|
| `REDIS_HOST` | همه | `redis` | hostname کانتینر Redis |
| `REDIS_PORT` | همه | `6379` | پورت Redis |
| `COLLECT_INTERVAL` | collector | `2` | فاصله زمانی بین هر reading (ثانیه) |
| `CPU_THRESHOLD` | alert | `80` | درصد CPU که alert رو فعال میکنه |
| `RAM_THRESHOLD` | alert | `85` | درصد RAM که alert رو فعال میکنه |

## ۷. نکته‌ای درباره `pid: host`

توی `docker-compose.yml`، سرویس `collector` با `pid: host` تنظیم شده.
این کار باعث میشه کانتینر namespace پردازشی سرور host رو به اشتراک
بذاره، که اجازه میده `psutil` آمار سرور واقعی رو گزارش بده، نه فقط
منابعی که داخل خود کانتینر دیده میشه (که به‌صورت پیش‌فرض محدوده و
نماینده خوبی از بار واقعی سیستم نیست).

اگه دید سطح host لازم نباشه (مثلاً برای یه محیط تست ایزوله‌شده)، میشه
این خط رو حذف کرد و collector به گزارش مصرف منابع خود کانتینر برمیگرده.

## ۹. محدودیت‌ها و بهبودهای ممکن

این یه پروژه با هدف یادگیریه، پس چند تا چیز عمداً ساده نگه داشته شده:

- **بدون persistence**: متریک‌ها هیچ‌جا ذخیره نمیشن، فقط زنده نمایش
  داده میشن. یه سیستم مانیتورینگ واقعی داده‌ها رو توی یه time-series
  database (مثل InfluxDB، Prometheus، یا حتی فقط append کردن به یه
  فایل لاگ) ذخیره میکنه تا بشه بعداً تاریخچه رو query کرد.
- **بدون authentication روی Redis**: توی یه محیط production، Redis
  باید پسورد و احتمالاً TLS داشته باشه، چون الان هر کسی توی همون شبکه
  میتونه وصل بشه و channel ها رو بخونه.
- **فقط یه سرور**: پروژه فعلاً فقط سروری که خودش روش اجرا میشه رو
  مانیتور میکنه. توسعه‌اش برای مانیتور چند سرور یعنی چند تا instance
  از collector اجرا بشه، هر کدوم پیام‌هاشون رو با یه hostname تگ بزنن
  تا dashboard بتونه بینشون تفاوت بذاره.
- **بدون اتصال به notification**: سرویس alert فعلاً فقط روی Redis
  پابلیش میکنه؛ هنوز ایمیل، پیام Slack، یا نوتیفیکیشن تلگرام نمیفرسته،
  که قدم بعدی طبیعی پروژه میتونه باشه.

## ۱۰. جمع‌بندی

این پروژه یه سیستم میکروسرویس ساده ولی کاربردی با الگوی ارتباطی
event-driven رو نشون میده. سه تا سرویس مستقل (collector، alert،
dashboard) کاملاً از هم جدا هستن و فقط از طریق channel های pub/sub
Redis با هم تعامل دارن، که اصل اساسی معماری میکروسرویس رو برآورده
میکنه: سرویس‌ها باید مستقل از هم قابل deploy باشن و نباید نیازی به
دونستن جزئیات پیاده‌سازی داخلی یا موقعیت همدیگه داشته باشن.
